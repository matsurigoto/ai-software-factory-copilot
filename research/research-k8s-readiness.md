# Kubernetes Deployment Readiness Report — On-Prem / Air-Gapped-Capable Cluster

All findings below are from direct fetches of official repos/docs (citations inline). Verdicts: ✅ K8s-native · 🟡 Runs on K8s with caveats · ❌ Not suitable for K8s.

> **更新（決策）**：公司採用 **Azure DevOps Services**（雲端 SaaS，唯一允許的雲端服務），因此下方 Azure DevOps Server 的 Windows VM 結論已不適用；僅保留 Azure Pipelines self-hosted agent（Linux 容器 + KEDA `azure-pipelines` scaler）在叢集內的部署模式，並需開通叢集出站白名單至 `dev.azure.com`。另 Azure OpenAI 亦已排除，模型一律為叢集內 vLLM 或公司內部 endpoint。

## Cross-Cutting Architecture Recommendations

- **Namespace segmentation by trust tier**: `ns-llm-infra` (LiteLLM, vLLM, Ollama), `ns-agents` (OpenHands, MAF, Goose, Aider, Qwen Code jobs), `ns-browser-automation` (browser-use, Playwright MCP, Midscene host runners), `ns-security-scan` (Trivy, ZAP, Nuclei, Schemathesis Jobs), `ns-observability` (Phoenix, ReportPortal, Allure), `ns-platform` (Onyx, Qdrant, Docmost, Temporal). Keep default `restricted` Pod Security Standard everywhere except where explicitly justified.
- **GPU node pool**: Label/taint a dedicated pool (e.g. `nvidia.com/gpu` label + `gpu=true:NoSchedule` taint), install **NVIDIA GPU Operator** once cluster-wide; required for vLLM (mandatory) and Ollama/whisper-asr-webservice (optional but recommended). For air-gapped clusters, pre-mirror driver-container images matched to the node kernel before cutting network access.
- **Sandbox node pool for untrusted agent code execution** (OpenHands/MAF/Goose/Aider arbitrary code execution, Phoenix eval sandboxes): dedicate a pool with **gVisor RuntimeClass** as the default for CPU-only untrusted workloads (no privilege needed, now GPU-capable via `nvproxy` if required) and **Kata Containers** for workloads needing stronger VM-level isolation or when nested-virt/bare-metal nodes are available. Avoid Sysbox unless a workload specifically needs Docker-in-Docker semantics (e.g., an agent building images).
- **Android/iOS mobile-test node pool** (Maestro, Midscene mobile paths): do **not** attempt to run Android emulators inside the general-purpose cluster — KVM passthrough on shared multi-tenant nodes is a real security/stability risk. Either stand up a separate bare-metal/nested-virt pool exclusively for this, or keep mobile test execution entirely outside K8s via a network-reachable device farm (physical devices over network ADB, or Maestro Cloud if egress is permitted).
- **eBPF/privileged workloads pool** (Keploy OSS, if used despite the caveats above): isolate to a small, explicitly privileged namespace/pool separate from the `restricted`-PSS majority of the cluster; prefer running Keploy on a dedicated VM/bare-metal host outside the cluster's trust boundary instead, given its OSS path effectively requires root and its only true K8s-native mode is commercial+cloud-tethered.
- **Windows workload exception — Azure DevOps Server**: this cannot run on Linux K8s at all (Windows Server + non-Linux SQL Server mandatory). Run it on a dedicated Windows Server VM (with SQL Server) entirely **outside** the Kubernetes cluster; only Azure Pipelines **agents** (Linux containers) belong inside K8s, scaled via the KEDA `azure-pipelines` scaler.
- **Stateful data-tier consolidation**: Most tools above converge on the same three dependencies — Postgres, Redis, and S3-compatible object storage. Stand up one hardened, HA Postgres cluster (e.g. CloudNativePG operator) and one Redis cluster (Redis Operator) shared across LiteLLM, Onyx, Docmost, ReportPortal, LangSmith Deployment, ZAP/report stores, etc., rather than one-off per-app databases, to reduce operational surface in an air-gapped environment.
- **Air-gap image/data mirroring checklist**: Trivy vulnerability DB, Nuclei templates, GPU Operator driver containers, Helm chart OCI artifacts (LiteLLM, vLLM, SonarQube, k6-operator, trivy-operator), and any LLM/Whisper model weights all require pre-staging into an internal registry/artifact store before cluster installation — none of this is handled automatically by the charts themselves.
- **MCP sidecar pattern**: For stdio-based MCP servers (Azure DevOps MCP, Playwright MCP in stdio mode), prefer either (a) same-pod process spawning when the consumer and MCP server share a container/pod, or (b) a `mcp-proxy`/`supergateway` sidecar container bridging stdio→SSE/HTTP within the pod, exposed via a ClusterIP Service for cross-pod agent access — avoiding the need for every MCP server to natively support network transports.
